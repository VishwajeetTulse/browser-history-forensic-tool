% ---------------- Abstract ----------------
\section*{Abstract}\label{sec:abstract}
\addcontentsline{toc}{section}{Abstract}
Web browsers silently record every website a user visits, every search they make and every file they download. In a digital forensic investigation this browsing history is one of the most valuable sources of evidence about a suspect's activities, interests and timeline. Modern Chromium-based browsers such as Google Chrome, Microsoft Edge and Brave store this history in a single SQLite database file named \texttt{History}. The file is locked while the browser is running, its timestamps are stored as microseconds since 1 January 1601 and the data is spread over several related tables, so it cannot be read directly or safely by an investigator.

This project presents the design and development of a Browser History Forensic Analysis Tool that automates the standard forensic workflow of acquire, preserve, analyse and report. The tool copies the History database to a working folder, computes a SHA-256 hash of the evidence so that its integrity can be proved later, reads the \texttt{urls}, \texttt{visits} and \texttt{downloads} tables, converts the WebKit timestamps into readable local date and time, and reconstructs a chronological timeline of the user's browsing activity. It also reports the most visited domains, daily activity, downloaded files and keyword search hits, and exports everything as CSV files and a self-contained HTML report that can be attached to a case file.

The tool is written in about 280 lines of Python using only the standard library, so it runs on Windows, Linux and macOS without installing anything extra. It was tested with a synthetic sample database and with the live Microsoft Edge history of a Windows 11 computer, and seven automated test cases verify every function. The result is a small, transparent and easily explainable forensic utility that demonstrates evidence handling, artifact parsing and timeline analysis.

\section*{Introduction}\label{sec:intro}
In today's world almost every activity passes through a web browser: searching for information, reading e-mail, shopping, banking, social media and downloading files. Because of this, the browser has become one of the richest sources of digital evidence. When a computer is examined in a cyber-crime case, an insider-threat investigation or a corporate incident, the first questions investigators ask are ``which websites did this person visit, when, how often, and what did they download?'' The answers are stored by the browser itself in its history database.

\textbf{Digital forensics} is the application of scientific methods to collect, preserve, analyse and present digital evidence in a way that is acceptable in a court of law. The National Institute of Standards and Technology (NIST) describes the forensic process in four phases: collection, examination, analysis and reporting. Two principles are central to every phase. First, the original evidence must never be modified; the examiner works on a verified copy. Second, the integrity of the evidence must be provable, which is done with cryptographic hash functions such as SHA-256: if the hash of the copy equals the hash of the original, the copy is identical bit for bit.

\textbf{Browser artifacts.} Chromium-based browsers (Google Chrome, Microsoft Edge, Brave, Opera) keep each user profile in a folder such as \texttt{C:\textbackslash Users\textbackslash <name>\textbackslash AppData\textbackslash Local\textbackslash Google\textbackslash Chrome\textbackslash User Data\textbackslash Default}. Inside it, the file \texttt{History} is a SQLite database with the following important tables:
\begin{itemize}[nosep]
  \item \texttt{urls} -- one row per unique URL with its title, visit count and typed count;
  \item \texttt{visits} -- one row per visit with the time of the visit and a reference to the URL;
  \item \texttt{downloads} -- one row per downloaded file with the saved path, source URL, start time and size.
\end{itemize}
Times are stored in the WebKit format: a 64-bit number of microseconds since 1 January 1601 UTC. To obtain the familiar Unix time (seconds since 1970) the value is divided by one million and 11\,644\,473\,600 seconds are subtracted.

\textbf{Problem.} Commercial forensic suites such as EnCase, FTK and Magnet AXIOM can parse browser history but they are expensive and work as black boxes. Opening the History file manually in a SQLite viewer is possible but slow, it offers no hashing, the timestamps remain unreadable and there is no report. Moreover, the browser keeps the file locked, so a careless examiner may fail to open it or may even alter it.

\textbf{Objectives of the project.}
\begin{enumerate}[nosep]
  \item To understand how Chromium browsers store history and downloads.
  \item To acquire the History file without altering the original and to prove its integrity using SHA-256.
  \item To convert WebKit timestamps into readable local time and reconstruct a chronological timeline.
  \item To provide useful analysis for an investigator: top visited domains, daily activity, keyword search and download listing.
  \item To generate CSV and HTML reports that can be attached to a case file.
  \item To keep the tool small, portable and easy to explain.
\end{enumerate}

\textbf{Scope.} The tool supports Chromium-family browsers on Windows, Linux and macOS. It does not parse Firefox (which uses a different file, \texttt{places.sqlite}), cookies, cache or saved passwords, and it does not recover deleted records. These are left as future work.

\section*{Methodology}\label{sec:method}
The tool follows the four-phase forensic process recommended by NIST. Each phase is implemented as a small group of Python functions in a single file, \texttt{bhft.py}.

\subsection*{1. Acquisition (collection)}
The examiner gives either the name of a browser (\texttt{--browser edge}) or the path of a History file taken from a seized machine (\texttt{--db path}). The tool copies the file into an output folder with a byte-for-byte copy. A byte copy is possible even while the browser holds the SQLite lock. It then computes the SHA-256 hash of the original and of the copy; if the two differ the tool aborts, because the integrity of the evidence cannot be guaranteed. The hash is printed and written into the report so that anyone can later verify that the evidence was not altered.

\subsection*{2. Examination (parsing)}
The copy is opened with Python's built-in \texttt{sqlite3} module in read-only mode (URI \texttt{file:...?mode=ro}). One SQL query joins the \texttt{visits} and \texttt{urls} tables and orders the rows by visit time:
\begin{lstlisting}
SELECT v.visit_time, u.url, u.title, u.visit_count, u.typed_count
FROM visits v JOIN urls u ON v.url = u.id
ORDER BY v.visit_time
\end{lstlisting}
Each WebKit timestamp is converted to local time with the formula
\[ t_{unix} = \frac{\mu}{10^{6}} - 11\,644\,473\,600 \]
where $\mu$ is the stored microsecond value. The \texttt{downloads} table is read in the same way. Every visit becomes a record with time, URL, title, domain, visit count and typed count.

\subsection*{3. Analysis}
Four simple analyses are performed on the list of visit records:
\begin{itemize}[nosep]
  \item \textbf{Timeline}: the records already sorted by time form the activity timeline; the first and last visit give the activity window.
  \item \textbf{Top domains}: the domain of each URL is counted and the $n$ most frequent are listed.
  \item \textbf{Daily activity}: visits are counted per calendar date to show on which days the user was active.
  \item \textbf{Keyword search}: a case-insensitive search in URLs and page titles (for example ``bank'' or ``invoice'') lists the visits of interest to the investigator.
\end{itemize}

\subsection*{4. Reporting}
The timeline and the downloads are written to \texttt{timeline.csv} and \texttt{downloads.csv} so they can be opened in Excel. A self-contained HTML report (\texttt{report.html}) is generated with the evidence details (source file, SHA-256, acquisition time, examiner machine), summary statistics, top domains, daily activity, keyword hits, downloads and the full timeline.

\subsection*{Algorithm}
\begin{enumerate}[nosep]
  \item Read command-line arguments (browser or file path, output folder, keyword, number of top domains).
  \item If the History file does not exist, stop with an error.
  \item Copy the file to the output folder; compute SHA-256 of source and copy; stop if they differ.
  \item Open the copy read-only; run the join query; convert each timestamp; build the visit list.
  \item Read the downloads table.
  \item Count domains and daily visits; filter visits by keyword.
  \item Write CSV files and the HTML report; print the summary on the console.
\end{enumerate}

\section*{Implementation and Results}\label{sec:impl}
The project consists of three Python files, available at \url{https://github.com/VishwajeetTulse/browser-history-forensic-tool}:
\begin{itemize}[nosep]
  \item \texttt{bhft.py} -- the tool itself (about 280 lines, standard library only);
  \item \texttt{make\_sample\_db.py} -- creates a realistic sample History database for safe demonstration;
  \item \texttt{test\_bhft.py} -- seven automated tests (pytest) covering timestamp conversion, hashing, parsing, keyword search, domain ranking and an end-to-end run.
\end{itemize}

The key function that converts Chromium timestamps:
\begin{lstlisting}[language=Python]
WEBKIT_EPOCH_DELTA = 11644473600   # seconds between 1601-01-01 and 1970-01-01

def webkit_to_datetime(micros):
    if not micros:
        return None
    seconds = micros / 1_000_000 - WEBKIT_EPOCH_DELTA
    return dt.datetime.fromtimestamp(seconds, dt.timezone.utc).astimezone()
\end{lstlisting}

\subsection*{Running the tool}
\begin{lstlisting}
python make_sample_db.py                                   # create demo database
python bhft.py --db samples/History --out output --keyword bank
python bhft.py --browser edge                              # live Edge profile
\end{lstlisting}

\section*{System Requirements}\label{sec:req}
The tool was developed on a Windows 11 laptop but, because it uses only the Python standard library, it runs on any computer that has Python 3. Below is the minimum system requirement for its use.

\subsection*{Hardware Requirement}

  \item 2 GB RAM

  \item pytest (optional, only to run the automated tests)
  \item Any web browser to view the HTML report; Microsoft Excel or LibreOffice to open the CSV files
  \item Visual Studio Code or any text editor for development
\end{itemize}

% ---------------- Conclusion ----------------
\section*{Conclusion}\label{sec:concl}
In this project a small but complete digital forensic tool for browser history has been designed and implemented. The tool acquires the Chromium History database without touching the original file, proves the integrity of the evidence with a SHA-256 hash, decodes the WebKit timestamps that make the raw data unreadable, and reconstructs a chronological timeline of the user's browsing activity. It summarises the most visited domains, daily activity, downloads and keyword hits, and produces CSV and HTML reports that an investigator can attach directly to a case file.

The implementation is a single Python file with no external dependencies, which makes it portable, transparent and easy to explain. Seven automated tests verify every function, and the tool was validated on both a synthetic database and a real Microsoft Edge profile.

The tool will be useful to forensic examiners, incident-response teams, students of digital forensics and anyone who needs to understand browser evidence. In future it can be extended to Firefox and Safari, to cookies, cache and form data, to recovery of deleted records from SQLite free pages, and to a graphical user interface.
